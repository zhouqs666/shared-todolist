## 一、这套组合是什么

| | 内容 | 性质 |
|---|---|---|
| **结构**（新① 时光章节） | 未完成区加小标题「要做的」；已完成按**完成时间**分章，每章一行小计：`今天 · 已完成 1 件` / `昨天 · 一起完成 2 件` / `更早 · 九月 · 一起完成 6 件` / `八月 · 一起完成 51 件` | 改 JS 渲染 |
| **视觉**（新Ⅰ 纸与光） | 未完成 = 新纸（白、浮起）；已完成 = 晒过的纸（暖一度、压平、内凹）。卡片尺寸、信息、位置全不变 | 改 CSS |

**两条核心约束**（来自你的原话）：卡片是原子，完成的待办不许缩成一行；隐藏款留在原位并被看得更清楚。

## 二、改动清单（逐文件）

### A. 纸与光 —— 纯 CSS，1 个文件

全部在 `public/css/style.css`：

| 位置 | 改动 | 说明 |
|---|---|---|
| `.todo`（现 779 行） | 圆角 16→20px、内距 15/16→17/19/16、阴影换双层暖影 + `inset` 白高光、底色改渐变 | 材质升级，尺寸/信息不动 |
| `.todo--done`（现 829 行） | 暖底 `linear-gradient(#fdf6f1, #f9efe8)` + `inset 0 2px 7px` 内凹，去掉投影；文字色转暖灰 | 「晒过的纸」 |
| `.todo__check`（现 875 行） | 18→20px，`opacity` .65→.85 | 未完成态更清楚 |
| `.todo--done .todo__check`（现 920–934 行） | **从 `opacity:0` 改成可见的撤销入口** | 顺手修现网缺陷：现在「取消完成」在界面上根本不存在，只能长按找菜单 |
| `.container`（现 462 行） | 顶部一层柔光 | 让卡片浮在光上 |

**⚠️ 两个级联陷阱（必须显式处理，否则线上会静默变样）：**

1. **稀有度会被吃掉**。`.todo--rare / --epic / --legendary` 在 2821 / 2828 / 2836 行，靠「排在 `.todo--done` 后面」取胜（都是单类选择器，后者胜）。新增的 `.todo` / `.todo--done` 若追加到文件尾部（4000+ 行），**级联上就赢过稀有度 → 线上 7 张隐藏款的渐变底全部变白**。
   → 做法：新增规则插在 2821 行之前；**更稳的做法**是把稀有度选择器提升为 `.todo.todo--rare`（权重 0,2,0），从此不怕后人追加。
2. **置顶 + 已完成 的组合**：`.todo--pinned`（847 行）现在排在 `.todo--done` 之后，所以「置顶且已完成」的卡片背景由置顶渐变赢。新增 `.todo--done` 若放到 847 行之后会反转这个行为 —— 要么保持原行为（放在 847 之前），要么改并说明。

**另：颜色要收敛为 token**。提案页里写的是硬编码值（`#fdf6f1` / `#8c7782` 等），实施时按仓库规则（AGENTS.md「组件只引用 semantic 层」）落到 `:root`：能复用 `--cream-*` / `--stone-*` 就复用，不足再补 1–2 个语义 token（如 `--color-surface-sunned`）。

**复杂度：S** ｜ 约 70 行 CSS、1 个文件 ｜ 工时 **2–3 小时**（含真机目测）｜ 无逻辑风险

### B. 时光章节 —— JS，2 个文件 + 1 个新纯函数

| 文件 | 改动 |
|---|---|
| `public/js/timeline.js`（**新增**） | 纯函数：`groupByLocalPeriod(todos, now)` → `[{ key, label, subtitle, todos }]`；`localDayKey(iso)` / `localMonthKey(iso)`；小计 = **只数件数**（贴纸小计已砍，见下） |
| `public/js/app.js` | `render()`（1261 行）里把章节头与 todo 一起排进同一个 `DocumentFragment`；新增 `renderChapterHeader` / `updateChapterHeader`（Map 复用，避免重建与重播入场动画）；章节内套用分组顺序 |
| `public/css/style.css` | 章节头样式（`.tl-chap` 及其内部），约 30 行 |
| `public/sw.js`（**计划外补充**） | 预缓存清单补 `/js/timeline.js` + `VERSION` v15→v16。**为什么必须动**：`/js/app.js` 是**缓存优先**策略，新增的模块靠"按需缓存"拿不到已缓存旧壳的浏览器 PWA 用户 —— 不递增版本号，他们永远停在旧 app.js。原生 App 不走 SW（`isCapacitorNative()` 直接放行），所以这条只影响 PWA 通道 |
| `state.js` | **不动**。`sortTodos`（152 行）保持原样：未完成仍在前 |

**⚠️ 头号实现坑（这是本方案最容易写错的地方）：**
`render()` 是增量渲染 —— 1325 行先用 `.todo[data-id]` 收集现有节点，1339 行把它们全塞进一个 fragment，最后 **1355 行 `todoListEl.appendChild(frag)` 把整个 fragment 移到容器末尾**。
如果章节头只是「插进去」而不参与这次搬迁，**第二次 render 之后所有章节头会挤到列表顶部，所有 todo 跑到下面** —— 看起来就是「章节全错位」。
→ 做法：章节头节点也必须按顺序 `appendChild` 进同一个 fragment（章节头用 `<li class="tl-chap">`、**不带 `data-id`**，所以 1325 行的 existing Map 天然忽略它，不会被删除逻辑误伤）。

**⚠️ 第二个坑：时区。** `completed_at` 是 `timestamptz`（UTC）。分组必须按**设备本地时间**取年月日：
用 `d.getFullYear() / getMonth() / getDate()`，**绝不能用 `toISOString().slice(0,10)`** —— 那会按 UTC 切天，北京时间晚上 8 点之后完成的事会被算成"昨天"。

**复杂度：M** ｜ 约 150 行（含新文件）｜ 工时 **4–6 小时**（含自测）｜ 三处风险：重排错位、时区日界、章节内排序

### C. 合计

**一次发布约 1 天**；建议拆成两次（见第六节）。无新依赖、无新字体、无原生代码。

**硬限制 / 未验证项（交付时要如实列出）**：

- 真机色偏、材质感受**无法在 CI 里断言**，只能人工看

  （`db.js setCompleted` 用 `new Date().toISOString()`），所以对方设备时钟偏快时，那条的完成时间可能落在未来。

  **不丢数据、不影响任何计数**（不变量用例守着）。要修必须先决定"以谁的时钟为准"，属产品决策，本次不做 ——

**最有价值的一条：那个「测试写了却抓不到 bug」的坑被提前堵住了。**
时区用例原本只在**非 UTC 主机**上有区分力，而 CI runner 恰好是 UTC —— 也就是说它会是个绿着的假测试。
对策是把同一组夹具放进 `TZ` 固定的子进程再跑一遍（`TZ=UTC / Asia/Shanghai / America/New_York / Pacific/Kiritimati / Asia/Kolkata`），
无论宿主机是什么时区都有区分力。变异实验证实：改成 UTC 切天后，`TZ=Asia/Shanghai` 等 4 个子进程全红。

**改前 / 改后 DOM 逐节点对照**（临时探针，用完已删）：同一份测试库数据，在 main 的 worktree（3199）
与工作区（3100）各渲一次 —— 27 项断言全通过，关键三条：

1. **未完成段与改前逐字一致**（分章确实没动未完成区）
2. **已完成段从"创建序 D,C,B,A"变成"完成序 A,B,C,D"** —— 正是本次要的那个变化，被明确钉住
3. **第二次 render 之后**章节头仍在原位（`[要做的 · 5] …卡片… [今天 已完成 4 件] …卡片…`），
   没有出现 PLAN 里警告的"章节全错位"
4. 隐藏款（`todo--done todo--legendary`）计算样式仍是 `linear-gradient(155deg, …)`，渐变底没被吃掉

## 九、顺序变更：到底改变了什么（用真实数据说话）

```
① pinned 在前 → ② 未完成在前 → ③ 按 created_at DESC（新创建的在前）
```

关键点：**已完成那一堆是按「创建时间」排的，不是按「完成时间」**。所以现在你完成一条创建于 8 月的旧待办，它不会去已完成堆的最上面，而是按 8 月的创建日期插进中部 —— 反馈是「它不见了，掉到下面某处」，唯一提示是那条撤销 Toast。

### 分章之后，组内排序**必须**跟着改（这是推导出来的，不是偏好）

如果章节按完成时间分（今天 / 昨天 / 八月），而组内仍按创建时间排，会得到两套坐标系：章头写「今天」，章内第一条却是「创建于 8 月、今天才完成」的。更硬的问题是**按 created_at 序遍历再切章会切出乱序的章节** —— 因为 `completed_at ≥ created_at`，但两者的序不单调：
创建 8/20 完成 8/25 的那条，在 created_at 序里排在「创建 8/1、完成 9/16」的前面，于是先被切进「八月」章，而更晚的「九月」章反而在后面出现。

→ 所以：**分章按完成时间 ⇒ 组内也按完成时间**。这就带出了下面这个可见的变化。

### 变化一（好的方向）：完成一条待办的反馈变明确了

改完之后，你刚完成的那条会落在**「今天」章节的第一条**（今天没有别的完成项时，就是紧随章头的第一条）。改动距离从「可能很远」变成「顶多跨过未完成区和一条章头」。

### 变化二（成本，实测很温和）：历史条目的相对顺序会重排

拿线上 60 条可比较的已完成条目算过：

| 指标 | 实测值 |
|---|---|
| 排序变化后位置变动的条目 | **22 / 60（37%）** |
| 中位挪位 | **1 位** |
| 平均挪位 | **1.6 位** |
| **最大挪位** | **4 位** |
| 跨越月份边界的条目（把"创建月"和"完成月"不同的挑出来） | **0 条** |

最后一行是关键：你的待办几乎都是**当月创建、当月完成**，所以「按创建排」和「按完成排」在你这批数据上高度重合 —— 最坏情况也只挪 4 位、中位数只挪 1 位。**这个改动在纸面上看着像动了大手术，实际几乎看不出来。**

### 分章之后你的列表会长这样（真实分布）

| 章节 | 条数（真实数据） |
|---|---|
| 要做的（未完成，无时间章） | 3 |
| 今天 · 已完成 | 按当天 |
| 昨天 · 一起完成 | 按当天 |
| 更早 · 九月 · 一起完成 | 11（9 月已完成总数，散在 9/1–9/13 共 8 天） |
| 八月 · 一起完成 | **47** ← 长章节 |
| 七月 · 一起完成 | 2 |

**要如实说的代价**：八月那一章 47 条，章头只在开头出现一次，你选了不吸顶 ⇒ **滑过这 47 条时没有坐标**（这正是提案里新④「吸顶月份轴」要解决的问题）。
如果哪天觉得迷路，最便宜的补丁是**在月内再切一层「周」章节**（8 月第一周 / 第二周…），数据现成、只多切一层，不需要动吸顶。先不做，等真机滑一周再判断。
