# 2026-10-09：订阅一张不存在的表 ⇒ 整个 Realtime 频道静默失声

**关联规则**：AGENTS.md 铁律二（交付前必须全面测试）／铁律六（审查 Checklist 维度 B）。
本条是**开发期抓到、未上线**的疑难 bug：它的形态足够隐蔽，值得单独记一条。

## 发生了什么

待办留言板（F-04 升级）引入两张新表（`todo_comments` / `comment_likes`），前端把它俩的
`postgres_changes` 订阅**挂在了既有的主频道上**（`todos-changes`，与 todos / 心里话 / 表情 / 图鉴同一条）。

开发期测试库还没建这两张表（SQL 待应用），于是跑全量 Web E2E 时出现这样一组结果：

| 用例 | 结果 |
|---|---|
| `test_pin` 步骤 8「对端**不刷新**就看到置顶章出现」 | ✗ 超时（10s） |
| `test_pin` 后续「对端取消置顶反向同步」 | ✗ 超时 |
| `test_blindbox`「对方升星实时同步到 star_level=2（UPDATE 通道）」 | ✗ 值没变 |
| `test_trash` / `test_offline` | ✗（均含跨端断言） |

**同时**：单端全绿 —— 登录、首屏、REST 增删改查、留言板弹层渲染全部正常；离线提示条不出现
（客户端自认"已连上"）；控制台没有 `CHANNEL_ERROR`。也就是说，**除了跨端断言，没有任何信号**。

## 根因（一行）

服务端无法为一张**不存在的表**建立变更订阅，于是**整条频道的事件投递被静默作废** ——
而客户端侧依然停在 `SUBSCRIBED`（`.subscribe(cb)` 回调拿到 `SUBSCRIBED`，`setOnline(true)`），
看起来一切正常。

## 为什么既有守卫拦不住（三点，缺一都不会踩）

1. **症状伪装成"服务抖动"**：频道状态是 SUBSCRIBED、没有报错、没有日志 ——
   第一反应会是"Supabase Realtime 又抽了"，而不是"我订阅了一张不存在的表"。
2. **单端路径完全正常**：REST 拉取、渲染、乐观更新都不经过这条链路（本项目 Realtime 只做推送，
   所有写走 REST）—— 所以只有**跨端**断言（"对端不刷新就看到"）才能暴露。
3. **顺序敏感**：只有"JS 先上、迁移后上"这个窗口期才会出现；窗口一过（表建好了）就自愈，
   复现窗口容易在排查中消失。

抓到它的正是**全量 E2E 的跨端断言**（`scripts/test_pin.py` 步骤 8 与 `test_todo_comments.py`
的同款断言）—— 这是"跑全量、跑双账号"的直接回报。

## 修复与防回归

- **修复（代码）**：留言的两张表订阅拆成**独立频道** `comment-changes`（`realtime.js` 的
  `initCommentRealtime`），并且**只在数据层确认两张表可读之后**才建立它
  （`comments.js` 的 `commentsTablesReady()` + `app.js` 的 `ensureCommentRealtime()`，幂等、可补建）。
  于是"迁移未应用"的窗口期只让留言功能自己不可见，主频道（todos / 心里话 / 表情 / 图鉴）不受影响。
- **防回归（审查 Checklist）**：已写进 `CODE-REVIEW.md` 维度 B —— 往 Realtime 频道加表之前先问
  「这张表在任何部署窗口里都可能不存在吗」；动到订阅的改动必须跑双账号跨端 E2E。
- **交付顺序（铁律三）**：SQL 先于热更。本次即使顺序反了，损失也被关在留言功能内 ——
  但**不要**把这条当成"可以不分顺序"的许可：顺序错了就没有发现机制，功能会静默缺席（不报错）。
- **可验证的证据**：修复后立即用双端探针复跑（A 加待办 → B 不刷新出现），并在表仍缺席的情况下
  复跑 9 个既有用例全绿 —— 证明"表缺席"这一维度真的被隔离住了（而不是碰巧好了）。
