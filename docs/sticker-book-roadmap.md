## 1. 背景与问题定义

**现状机制**（代码锚点见附录 B）：12 张贴纸（rare / epic / legendary 各 4 张，两人共享一本），
添加待办 15% 开出隐藏款，命中后只在**未集齐的档位**按 6:3:1 归一抽选，逐个补序号解锁。
机制本身健康——权重归一让长尾不痛苦。

**问题：集齐之后只有三处收尾**——

| # | 集齐后的现状 | 位置 |
|---|---|---|
| 1 | 开奖提示退化为「图鉴 12 张已全部集齐，这张留作纪念 ✨」 | `public/js/blindbox.js:348-353` |
| 2 | 抽奖池回落三档全池：开奖照常（配色 / 撒花 / 对方端揭晓都在），**收益归零** | `public/js/blindbox.js:223-228` |
| 3 | 金色完成态 + 一次性庆祝，之后图鉴变陈列柜 | `public/js/sticker-book.js:158`、`:247-249` |

**核心诊断**：这套系统的情感引擎是「添加待办 → 15% 惊喜」。集齐前惊喜 = 收益；集齐后惊喜只剩特效。
所有升级玩法都在回答同一个问题：**集齐之后，15% 那一刻还剩下什么？**

**节奏数据**（按真实掉落算法 3 万轮蒙特卡洛模拟，复核方式见附录 B）：

| 指标 | 数值 |
|---|---|
| 集齐所需添加数（两人合计） | 均值 80 / 中位 78 / p10 54 / p90 108 |
| 最后一张的档位 | 92.6% 是传说款（低权重档天然压轴，无需改造） |
| 仅剩一档时的长尾 | 每次隐藏款必落该档，均值 ≈ 6.7 条/张 |

**结论：集齐是正常使用 1-2 个月内必然发生的事。** 本文档全部设计以「集齐是常态」为前提。

**定位**：把图鉴从「待办的彩蛋」升格为产品第二主线——**收集与纪念**。

## 5. 批次 2：地基（key 系列化 + 书架骨架 + 主题残留清理）

**解决的问题**：为多册图鉴做结构与命名准备，顺手清主题残留。**无用户可见内容产出，可独立合并。**

### 5.1 sticker_key 系列化（本路线最重要的一次重构）

- **方案（已定）**：**语义前缀**。第一册 key 保持无前缀（解析时视为 v1）；后续册用册短名前缀——
  第二册 = `story_rare_1` … `story_legendary_4`
- 解析收敛为 blindbox.js 导出的**单一函数 `parseStickerKey()`**：
  正则 `/^(?:([a-z0-9]+)_)?(rare|epic|legendary)_(\d+)$/`，series 组缺省 = v1；
  维护"册短名 → 册定义"注册表，**禁用 `rare` / `epic` / `legendary` 作为册名**（防解析歧义）
- **为什么不用"加 series 列"**：免 DB 迁移、key 自解释、DB 里的行肉眼可读；
  两种形态的兼容成本由 `parseStickerKey()` 单点承担。DB 对 key **没有格式约束**
  （RLS 探针 `check-rls.mjs:91` 用 `'rls-probe'` 这种自由 key 也能插入），前缀方案零迁移
- **影响面**（2026-10-03 全仓 grep 快照，动手时**必须重新 grep** 为准）：
  - **有格式假设、必须适配**：`blindbox.js:129` / `:143`（两处裸正则）、`blindbox.js:319`（key 构造——本批次保持 v1 行为不变，批次 3 时改为带前缀）
  - **无格式假设、不用动**：`state.js:216`（按 key 幂等）、`transforms.js:74`（字段映射）、
    `db.js:499-516`（upsert `onConflict: 'sticker_key'`）、sticker-book.js 其余查找 / 已看集合（前缀天然区分两册）
  - **测试脚本**：`test_sticker_wiggle.mjs:41-43` 与 `test_blindbox.py:150` / `:349` 构造无前缀 key——批次 2 **不改**（v1 行为零变化）；批次 3 增加 story key 用例
  - `reset-test-db.mjs` 硬删 stickers 全表，不依赖 key 格式

### 5.2 图鉴书架骨架

- sticker modal 升级为**多册结构**：册 tab（本批次只有 v1 一册真实内容）+ 按册渲染（`buildFullBook` 系列化）
- v1 金色完成态、红点、已看集合（localStorage `seenStickerKeys`）逻辑**按册隔离**（key 前缀天然区分）

### 5.3 主题残留清理（3 处）

## 7. 批次 4：升星（闪卡 / 烫金）

**解决的问题**：所有已上线册**全部集齐后**的终局收益；图鉴可收集空间 12 → 36 态。

- **数据**：`stickers` 加 `star_level SMALLINT NOT NULL DEFAULT 0`

  先 `--project test --apply` 幂等自证，再 `--project prod --apply --confirm <文件名>`；

- **升星规则**：升星期内开出隐藏款 → 该册该档**最低序号的未满星贴纸** +1 星；星级 0 / 1 / 2 = 普通 / 闪卡 / 烫金（上限 2）
- **并发**：UPDATE 带乐观守卫 `WHERE star_level = <期望值>`，0 行更新则顺延下一张
  （与现有"撞序号自愈"同一思路：以数据库结果为准，不信本地计数）
- **UI**：格子星级角标 + 故事卡显示星级
- **数学预期**：升满一册 ≈ 再 ~160 次添加（24 次升星事件 ÷ 15%；2026-10-04 更正，此前误写 ~80）
- **特效**：升星瞬间动效按 D6 判据——先手写，达不到"惊喜级"再考虑库
- **验收**：`test_blindbox.py` 扩展（**全部册集齐后**强制开奖 → 星级 +1、满星顺延、双端同步）；
  迁移幂等自证输出贴进 PR 描述
